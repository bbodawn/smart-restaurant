# 为什么采购数量要交给代码，而不是大模型

> 一句话主题：**确定性问题 → Python；非确定性问题（解释/见机行事）→ LLM。**
> 这一篇专门把“为什么数量必须代码算”讲透。

---

## 1. 一个具体例子

假设食堂看到：

```
现有库存  = 40 kg
每天消耗  = 20 kg
未来 3 天 大概需要 = 20 × 3 = 60 kg
安全库存   = 一些我们认为不该跌破的底线
```

如果现在补到刚刚好能撑到补齐的那天，采购量大概这么算：

```
理想量 ≈ 未来 3 天需求 − 现有库存 = 60 − 40 = 20 kg
```

这是一个**很简单的减法**。

- 能不能犯错？不能。算错要么断货，要么多塞库存、浪费钱。
- 需不需要“理解”“创作”？完全不需要。

> 结论：这种确定性的加减法，应该由写死的代码一次算对，而不是让大模型“猜”一个数。

---

## 2. 为什么大模型不适合干这种活

大模型很擅长“组织语言、讲故事、总结、推断模糊问题”。但它不适合干“精确算术”，因为：

- 它是在“猜下一个词”，即便算 20 加减也可能给你 19.8 或 19.999 这种浮点尾巴。
- 金额、库存是真金白银和真实数量，一个数错了就是采购错。

所以我们把算术放进显式规则代码里，结果稳定可复现、可审。

> 专业名：这种“写死规则、结果可预测、与模型无关”的计算叫 **deterministic（确定性）**。对应代码节点就是 `deterministic_policy`。

---

## 3. “制度表”到底怎么判

这套制度我简化成一条链，真实代码在此基础上再加 `risk_flags`：

1. 只要 `现有库存 ≥ 未来3天需求 且 现有库存 > 安全库存` ⇒ **不用买（NO_PURCHASE）**。
2. 否则要考虑补货：
   - 若 `报价比历史贵 > 20%` 或 `现有库存 ≤ 安全库存(已贴/跌破底线)` ⇒ **REVIEW，要请人审**；
   - 其 他（只是比未来 3 天少、价格正常、还没跌破底线）⇒ **自动买（PURCHASE）**。
3. 当确定“要买”，会把 `quantity` 与金额也一并算出（同样写成代码，不是模型给的）。

> 记住代码里采购判断继续沿用“需求 = 日销量×3”，没改，还是那个简单预测口径。

---

## 4. 那 Agent5 / LLM 在这个项目里还干嘛？

它不负责算数。它负责在 **REVIEW** 这种事上写“解释”：

- 为什么触发了复审（例如报价高了 25%）。
- 库存风险大概什么样。
- 建议怎么给采购的人看。

也就是它负责**把风险讲给人听**，而不是**拍板买多少**。数量永远由制度表代码来给。

---

## 5. 一眼记住整条认知

```
确定性的（加减乘除/规则判断/金额）→ 交给 Python（deterministic）
会出错也怕出错的“真金白银量”   → 更不该交给 LLM
需要总结/解释/自然语言的       → 交给 Agent5（LLM）做“顾问”
```

> 所以面试问到"为什么买多少不用 LLM"，回答要点：采购量是必须精确且可审计的确定性计算，放进大模型会引入不确定性；我们把这类算交给写死的规则函数，只有“向人解释风险”这类开放输出才交给 LLM。

---

## 6. 本实现是否有超能力？——没有

本篇描述的都是代码里真实存在的最小规则：简单 3 日乘法 + 比价判断 + 阈值。它**不是**高级需求预测、也不是 3~7 天健康区间、更不是靠模型乱拍。别把文档写得比代码聪明。
