# 项目里真实踩过的坑 · Problem History

> 这篇不是“系统可能存在问题”，而是我真实做这个系统时遇到的四个坑：当时是什么问题 → 为什么发生 → 怎么发现 → 怎么解决 → 学到了什么。

---

## 坑 1：Auto Procurement 扫描的范围和 Policy 的采购规则没对齐

**当时是什么问题**
自动巡检只会去找“库存 ≤ 安全库存”的食材。

**为什么会发生**
早期自动采购粗浅地写成：低于安全线才补货 → 于是它只会发现“已经跌破/贴着安全线”的食材。

**我当时为什么没想到**
那时把“自动巡检该扫什么样”和“政策到底什么条件下该买”当成两套独立而没仔细对齐的东西，默认它们一致。

**怎么发现的**
真实跑了一遍 `scan_and_trigger_procurement`，发现被自动扫进去的食材，在 `deterministic_policy` 里**几乎全都触发安全线风险→ 走 REVIEW / 需要人工**；原本“库存低于未来 3 天但没跌破安全线、可以自动补”的 PURCHASE 场景，反而根本不会被扫到。也就是说：理论上永远很少发生“自动补货一气呵成(COMPLETED)”。

**怎么解决**
把巡检的扫描条件从 `current_stock <= safety_stock` 改成与采购口径一致：去扫 `current_stock < daily_sales * 3`（即低于“3 天预测需求线”），再让 `deterministic_policy` 决定扫进去的食材到底是自动(PURCHASE)还是请人审(REVIEW)。PURCHASE 的食材这才真正进入能直接入库的路径。

**学到**：**入口/候选条件必须与核心决策规则保持一致**——扫进来的范围要对得上政策判断的分档，否则“能自动”的能力相当于被埋没。

## 坑 2：采购数量这个“数据契约”放错位置

**当时是什么问题**
Graph 明明判定“应采购 20kg”，最后订单却没真正入库。

**为什么会发生**
新的流程把“该买多少”写在 `policy_decision.quantity = 20`；
但旧的自动采购代码仍旧去读 `state["quantity"]`，它在这个新流程里一直是 **0**。

于是：

```
Policy 决定买 20
  ↓  Service 读到旧字段 quantity = 0
  ↓  因为 quantity=0 → 不写 order item、不执行入库
  ↓  订单显示 PURCHASE_CREATED，但库存没加
```

看着“成功建单”，其实仓库一滴没进——这是非常隐蔽的一类 bug。

**怎么发现**
真实 MySQL + Redis 跑自动采购，从数据库核对 `inventory.current_stock`，发现根本没有增加。

**怎么解决**
统一成：**采购数量以 `policy_decision.quantity` 为准**，Service 把它写进 `purchase_order_items.quantity`，再由 `execute_inbound_stock` 入库。不再依赖那旧的顶层字段。

**学到**：**多 Agent / 工作流系统里的高破坏性 bug，往往不是“某函数算错了”，而是“不同模块对同一个概念到底放哪儿理解不一致”。** 定好 data contract（谁是成交真相）极其重要——这也是面试上很能讲的一点。

## 坑 3：REVIEW 曾经没有真正落地“人工审批”

**当时是什么问题**
流程里 `REVIEW` 光有标记，没有真正进入会让流程暂停的 human-in-the-loop。

**为什么会发生**
最初在“新链路”里 REVIEW 只是结束节点；但外部 Service 拿到结果时，用一种朴素逻辑“这次没有 interrupt = 没有风险 = 可以自动照着执行”，于是高风险 REVIEW 也可能被当成可自动跑的普通单去执行入库。
这就是没有把“该请人审”和“没有发生 interrupt”区分开的隐患——实际上"没有中断"并不等于"没风险"。

**怎么解决**
把 REVIEW 明确串成：
```
REVIEW → Agent5(解释风险) → HITL(interrupt 等人) → 通过则继续采购/拒绝则结束
```
这样高风险单在真正落库前必须停下来等人点头，杜绝“REVIEW 被绕过直接自动执行”。

**学到**：在带 If 分支的采购系统里，**风险分支必须强制进人工，而不能靠“外部是不是恰好没中断”这种隐式信号去猜测**。

## 坑 4：多 Worker 的 check-then-act 竞态

**当时是什么问题**
让自动巡检多个机器一起跑时，同一个食材可能被创建两张订单、各加一次库存（本想 +20 却变 +40）。

**为什么会发生**
代码是先做“查这个食材有没有进行中的订单”(`_has_open_order`)，没有才去建单。这叫 check-then-act（先查再做）。两个 Worker 几乎同时执行：

```
Worker A：查 → 没有进行中
Worker B：查 → 没有进行中
A: 建单、入库 +20
B: 建单、入库 +20
```

两者在“查”和“建”之间谁也没拦住谁。

**怎么解决**
三层式保护：
1. **Redis 食材锁（Ingredient Lock）**：按食材把整段“查单→建单→入库”串行；抢不到就跳过这个食材。
2. **DB open-order 检查 `_has_open_order()`**：再加一道账本检查当兜底。
3. **入库幂等 `execute_inbound_stock()`**：订单已完成就不会再 +一次库存。

并且做了真实并发测试：同一种食材两个 Worker 一起触发，最终**只有 1 笔订单、只有 1 次库存 +N**。

**学到**：并发下“查了再建”并不是保险，要用**锁（互斥）**真正把关键区串起来；数据库的幂等兜底亦不能省。仅靠一句 `_has_open_order` 会自欺欺人。

## 结尾：如果能穿越回过去，我第一件会修什么？

- 开工第一版就应把 `policy_decision.quantity` 定为唯一成交数量、并写清 State → DB 映射的文档——坑 2 能全省掉一半调试。
- 巡检入口条件直接复用政策同一条“3 天预测线”，避免坑 1 白跑。
- 复审(RISK)一出现就走 HITL、并发就按食材上锁——这样坑 3、坑 4 在早期被拦下，而不是测试阶段才发现。

> 这些不是编的，是 RDP 真实踩过后靠“真实 MySQL + Redis 反复查库验证”抓出来的。
