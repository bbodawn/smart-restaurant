# 为什么同一个食材不会被重复采购/重复入库 · Concurrency And Idempotency

> 一句话主题：三个人可能同时盯上“猪肉该补”，怎么保证**只下一笔单、只加一次库存**？

---

## 1. 先用小故事看最坏情况

假设系统每天自动扫食材，有两个 Worker（可以理解成两个同时跑的程序/机器人）都发现：鸡肉库存低了，该补 20kg。

如果没有保护，可能发生：

```
A：先查“有在进行中的鸡肉采购单吗？” → 没有
B：也查“有在进行中的采购单吗？”    → 也没有

A：创建订单 A
B：创建订单 B

A：库存 +20
B：库存 +20

最终 库存只该 +20，却变成 +40
```

这是典型的“**先检查、再行动（check-then-act）**”竞态：两个人都先查到了“没有单”，然后各自各建了单。看起来每一步都对，错就错在“查”和“建”之间没有互相拦住。

---

## 2. 我们用什么来挡住它（三层保护）

光靠一个动作不够，三层各防一件事：

### 第一层：Redis 食材锁（Ingredient Lock）——门锁
在“查有没有单→下单→入库”这段关键线上，先给**这个食材**加一把 Redis 锁。

- Worker A 抢到锁 → 开始处理鸡肉
- Worker B 同一时间也想锁同一食材 → **抢不到，跳过这个食材**（不等待，去忙别的食材）

这样就只有一个程序能进这笔食材的“处理房间”。

> 注意锁按“食材”粒度的原因：不同食材（鸡肉/大米/酱油）互不干扰，可以并行；只有同一个食材才需要互斥。所以**不是**给所有食材上一把全局锁（会把本该并行的都压成串行）。

### 第二层：数据库检查 `_has_open_order()` ——查账
在最终建单前，再查一次**数据库里这个食材有没有“还没结束”的采购单**（RUNNING / PURCHASE_CREATED / SUSPENDED 之类）。有的话直接跳过。

> 它不是能独立解决一切的，但当锁意外失效/过期时，它是一道额外的“看账兜底”。

### 第三层：入库幂等 `execute_inbound_stock()` ——防重复执行
真正加库存的函数做了一个小动作：如果订单**已经标成 COMPLETED**，就不会再给它 +一次（直接返回“已经完成”，不动库存）。

> 就算同样的“给这张单入库”被重复触发，库存也只加一次。这个“重复做不造成重复结果”的品质，叫 **幂等（Idempotency）**。

---

## 3. 三层为什么要分开讲

| 保护 | 防的是什么 | 类比 |
| --- | --- | --- |
| Redis 食材锁 | 两个 Worker 同时进同一烹饪过程 | 门口一把锁 |
| 数据库 open 单检查 | 某一刻没锁但已有在进行单 | 下厨前对账，看是不是已经有人在做 |
| 入库幂等 | 同一种已完成的动作反复执行 | 已发的快递不会因为扫两次就再发一箱 |

> 这三样不是同一个东西，谁也代替不了谁。

---

## 4. 人工审批那头的并发也类似

人类也可能双击“通过”，或“通过”和“拒绝”几乎同时点到。

做法与上面呼应：

- 一单审批同一时间只放一个请求处理（审批接口有 order 粒度锁＋数据库状态检查）。
- 一旦单已变“完成/拒绝”，后来的人再点什么都会被挡下来，不会真的再加一次库存。

所以即使你**连续点两次通过**，最终也只入一次库；“通过 vs 拒绝”并发乱点，最终要么是完成、要么是拒绝——不会同时出现“又完成又拒绝、库存被增两次”这种矛盾态。

---

## 5. 面试一句总结

问题：“怎么防止两个 Worker 同时采购同一个食材、重复入库？”

答：三层。先给食材拿一把 **Redis ingredient lock**，把“查单→建单→入库”这段按食材串行；再保留数据库的 **open-order 检查**作异常兜底；最底层 `execute_inbound_stock()` 还弄成**幂等（已 COMPLETED 不再 +）**。三者分别防“并发双进”“无锁时的已有进行单单”“同一动作重复”。真实并发测试中，同一种食材触发两次最终只有一条订单、库存只加一次。
