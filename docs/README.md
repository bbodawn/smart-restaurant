# 如果你已经忘记这个项目了，先看这里

这是“智能食堂采购系统”的项目知识库入口。
如果你一个月没碰这个项目，请从这篇开始，按顺序花 5 分钟重新建立认知。

---

## 第 1 分钟：这个项目到底在干什么？

一句话：

> 每天自动检查食堂的食材库存，发现“未来可能要不够吃”的食材时，自动决定要不要采购；普通情况直接自动补货，价格异常或库存很危险时暂停下来交给人类审批，审批通过后真正把货补进库存、并把订单存进数据库。

更细一点（5 句话）：

1. 系统每天“巡视”所有食材：只要“当前库存 < 未来三天的预计消耗”，就进入分析流程。
2. 三个小分析员分别查看：库存还够不够撑 3 天、价格比历史贵了多少、这家供应商是谁。
3. 一个“规则裁判”（不是 Llama）用固定数学规则算出：要不要买、买多少、金额多少——只有普通低风险才自动买。
4. 一旦价格太贵（偏离>20%）或库存已经贴到安全线，就不会自动买，而是先请一位“风险分析顾问”把风险讲清楚，再暂停下来请人类点“通过/拒绝”。
5. 人类点“通过”后，系统把真正要买的数量写进订单、把库存真正增加，并标记订单完成；“拒绝”就暂停不买。

记忆口诀：**看库存 → 算规则 → 高风险请人拍板 → 落库存。**

---

## 第 2 分钟：流程长什么样？

```mermaid
flowchart TD
    A[系统发现：库存 < 3天需求] --> P[同时(并行)跑三个分析]
    P --> A1[库存分析 够不够撑3天]
    P --> A2[价格分析 贵了多少]
    P --> A3[供应商是什么(快照)]
    A1 & A2 & A3 --> D[规则裁判 Policy]
    D --> N[不买 NO_PURCHASE]
    D --> B[自动买 PURCHASE]
    D --> R[高风险需人工 REVIEW]
    B --> BB[普通补货: 写订单+入库存]
    R --> C[风险顾问 Agent5 解释风险]
    C --> H{人类审批}
    H -->|通过| OK[真正写订单 + 库存真正增加]
    H -->|拒绝| NO[不买 结束]
```

如果你完全看懂了这张图，基本上就重新找回了项目主体。

（专业名后的解释：三个小分析“同时干活”在 LangGraph 里叫 **Fan-out / Fan-in（并行+汇聚）**；“规则裁判”叫做 **deterministic_policy**；“风险顾问”就是文档里的 **Agent 5**；“人类审批”就是 **HITL（人在回路）**。）

---

## 第 3 分钟：每个“角色”一句话

- **库存分析员（inventory_analysis）**：用固定公式算库存能撑几天、够不够 3 天需求。纯 Python，不喊大模型。
- **价格检查员（price_analysis）**：算“供应商现在报价 比 历史均价 贵了几个百分点”。也是算术。
- **供应商信息员（supplier_analysis）**：只把“这家供应商是谁、报价多少”照抄出来做快照。**注意：它没有做多供应商比价选优**，别把它说成“智能选商”。
- **规则裁判（deterministic_policy）**：用“如果库存 >= 3 天需求且 > 安全线 就不买；价格偏离>20% 或库存贴线就 REVIEW”这类固定规则决定 买/不买/请人审。
- **风险顾问（Agent 5）**：唯一的 LLM 角色。它只看已算好的结果，把“为什么触发复审、有什么风险、建议怎么做”写成人类看得懂的报告。
- **人类审批（purchase_approval / HITL）**：人工点“通过 / 拒绝”。
- **采购执行/入库（Service / execute_inbound_stock）**：真正把数量写进采购订单、把库存数字 +N、把订单标成完成。
- **Redis**：两个用途——(1) 给“暂停后继续执行”存工作状态；(2) 给“同一食材别被两个机器人同时下单”当一把门锁。
- **MySQL**：长期保存真正的订单、供应商、库存数据。

---

## 第 4 分钟：三个最重要的设计原则

1. **确定性计算交给代码，非确定性分析交给 LLM。**
   “买 20kg”这种是算术，让 Python 算；只有“这段库存风险怎么讲给人听”才用大模型，防止大模型嘴上说说就把库存/金额弄错。
2. **决定是代码说了算，风险解释是顾问说的，最终授权归人。**
   数量、金额永远来自 `deterministic_policy`；Agent 5 只有解释权绝不能改数量/改判断；能否真正花钱由人类在流程中拍板。
3. **真正执行库存/入库归 Service，并且上数据库事务与幂等保护。**
   agent/graph 不会自己写数据库；真正 +库存、标 COMPLETED、防重复入库的事都收敛到最下层服务，保证“要么一起成功、要么都不成”。

---

## 第 5 分钟：三个最容易忘的坑（详见 problem-history.md）

1. **`policy_decision.quantity` 才是“这次要买多少”的唯一来源**；旧的顶层 `state["quantity"]` 在这个新流程里一直是 0。
   如果代码读错位置，会“看着像买了，实际库存一点没加”。
2. **只要判定 REVIEW，就必须走 Agent5+HITL 人类审批**；绝不能因为流程“没有发生中断”就以为“没风险、可以自动执行”。
3. **Auto Procurement 要多台机器同时跑时，必须给“同一个食材”上一把食材粒度的 Redis 锁**；单靠“先查有没有进行中订单”这一步仍然可能两个人同时查/同时下单。

---

## 当前能力边界（一句话）

是一个正确的 MVP：并行分析 + 固定规则采购 + LLM 风险解释 + 人工审批 + 可恢复 + 自动采购 + 并发保护。
**没有**：真正的 3~7 天健康区间、高级需求预测、真正多供应商比价、供应商评分、价格趋势预测、ABC、保质期管理。这些以后可能做，但现在没有。
