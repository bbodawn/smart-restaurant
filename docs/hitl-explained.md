# 为什么要有“人工审批”（HITL）

> 一句话主题：**确定规则发现风险，Agent5 解释风险，真正拍板买不买的是人，真正改库存的是 Service。四个角色分工不许混。**

---

## 1. 先讲一个例子：价格涨了但没涨太多也能不代表等

假设某食材的**历史均价是 25 元**，现在供应商报 **32 元**。涨幅大约是 `(32−25)/25 = 28%`，明显**超过 20%**。

这时系统不能像人一样一拍脑袋说：

- 反正涨了，不能买 → 不对，可能下个批次更贵，还是要补；
- 或者我了解行情，这价能接受，直接买了吧 → 那是机器自作主张，没人担责。

系统选择一个更稳的姿态：

> “这是高风险（价格偏差>20%），我把库存、价格、供应商、风险都整理好，放慢，**请一个人类来拍板**。”

这就是 **HITL（Human-in-the-Loop，人在回路）**——让一个人来决定“过/不过”。核心是：**风险不高的可以自动，一旦有风险，把解释交给风险顾问、把授权交给人。**

---

## 2. 四层角色分清楚

| 层 | 角色 | 干什么 | 谁来做 |
| --- | --- | --- | --- |
| 1 | 规则裁判 `deterministic_policy` | 用制度认定“这是 REVIEW” | 纯 Python 制度 |
| 2 | 风险顾问 `Agent5` | 解释为什么风险、风险多大、建议怎么做 | LLM |
| 3 | 人工 `HITL` | 最终点“通过 / 拒绝” | 人 |
| 4 | 采购执行 `Service` | 真正下单 + 改库存 | 后端服务 |

把这四层拆开的原因：

- 制度规则算风险是**确定又可靠**的（Python 不会看走眼）。
- 但“风险到底意味着什么、怎么写给人看”是**开放的**（适合 LLM 组织语言）。
- 而**要不要真花这笔钱、这段库存安全责任**，机器承担不起，给人。
- 最后真去动数据库/库存是**纯业务**，交给有事务的 Service。

> 如果让 Agent5（或让 LLM）直接“决定买”→ 它既没有责任感也有不确定性；如果让制度直接自动买风险采购 → 又少了一道人行审计。这就是为什么 REVIEW 必须落在“解释 → 人审 → 再执行”。

---

## 3. 一次“暂停再继续”具体什么样

走到 REVIEW：工作流会调用内部“暂停（interrupt）”能力，把当前状态存到 Redis 存档，并把你需要的那笔信息整理出来拿给人看。

后台出现“待审批”订单。人在前端点【通过】：

- 系统用同一个存档号把工作流“唤醒”，让它**从刚才停下那一段继续**。
- 不是重头把三个分析又跑一遍。

> 可以把它想成“游戏或写代码到一半先存档保存，下次直接接着写”，不重头再来。
> 技术上这是 `interrupt()` + Redis `Checkpoint` + `Command(resume=...)`。

人点【拒绝】：则直接结束，并标记这笔单为“已拒绝”；不会真去下单/入库存。

---

## 4. 没这个会怎样（为什么重要）

- 如果把 REVIEW 当成“普通无风险单”接着自动执行→ 高风险采购会绕过人工，可能买到贵价却没人签字。
- 如果 Agent5 自说自话“我批了，我不写” → 系统在拿钱与库存当儿戏。

一句话闭环：**规则发现问题(Python) → Agent5 讲人话 → 人类签字 → Service 执行入库**。

---

## 5. 红线：谁都没实现的能力

我们**没有**项目能力里出现这种东西：Agent5 自己改数量/改制度、Agent5 自己跑数据库、Agent5 绕过 HITL 直接给 APPROVE、也不存在机器把人架开自动批准。别把它写成"AI 自我操控";只有 Human 能给 final 授权。
