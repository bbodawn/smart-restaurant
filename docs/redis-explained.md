# Redis 在这里到底负责什么 · Redis Explained

> 一句话主题：Redis 在我们项目里**干的是两件完全不同的活**，一定要分清：
> **Redis Checkpoint（工作流程的存档点）** 和 **Redis Lock（仓库门锁）**。

---

## 1. Redis 是一台什么服务器

先定位 Redis：它是一块非常快、能带点网络的“临时缓存/数据库”，常被用来存很快读写的 Key-Value(键值)。

在本项目里它主要干这两件事，风格迥异，放在一起容易绕，我们分开讲。

---

## 2. 用法一：Redis Checkpoint —— “游戏存档”

### 干什么
人工审批发生在流程中间，会让 LangGraph **暂停**在那里等人。可程序不能永远停在内存里（服务可能重启），我们得把“现在做到了哪一步/该从哪续”记住。

Redis Checkpoint 就是这么个存档：它把工作流执行到某一步**在哪存了档**、正在做的事一些必要的中间状态保存下来，还用一个 `thread_id`（一次流程的标识号）当索引。

### 类比
打游戏时存个档。这次存到“第八章的一半”，下次我不需要从头玩第一章，直接读档。

### 在项目里怎么用
- 走到 REVIEW、触发 human-in-the-loop 暂停时，LangGraph 会在这里落一个 checkpoint。
- 之后人工在后台点了【通过】，系统拿到同一个 `thread_id`，用 `Command(resume=...)` 说“我从存档继续”，于是**从暂停点接着往下**，而不会把前面三个分析、制度表又从头复跑一遍。

> 如果连 Redis 都没有（存不了档），我们还能靠“从 MySQL 里把订单需要的字段再拼一份”近似恢复执行——这是额外的兜底，不是常态。

---

## 3. 用法二：Redis Lock —— “仓库门锁”

### 干什么
系统的自动巡检可能有多台机器（或者说多个同一时刻跑的 Worker）同时在扫库存。假如两个 Worker 都发现“鸡肉该补”，如果不拦一下，它们可能同一时刻各建一单、各加一次库存，最后补重复了。

Redis Lock 就是一柄“门锁”：同一个食材同一时间只让一个程序拿到钥匙进去处理；另一个程序抢锁抢不到，就跳过这个食材去忙别的。

### 类比
仓库门口一把锁。A 拿了钥匙进去，B 到门口发现锁着，就去仓库/出口先管别的食材，不盲目硬冲。B 不会傻等整批，别在一个食材上干耗。

### 在项目里怎么用
- 锁的名字按“食材”来区分（如 `lock:auto-procurement:ingredient:鸡肉`），所以大米和酱油可以同时被别人各处理，互不影响；只有同一个食材才需要排队。
- Redis“拿到就成，抢不到返 ‘失败’”的特性，被我们利用成：拿不到锁就跳过这个食材继续扫下一个，不把整轮自动采购卡死。

> 顺带——审批用的“order 锁”也是同类型的 Redis 锁，不过 key 是订单，管的是同一笔订单别被两个人同时批乱套。

## 下面是常见混淆点（面试高频）

| | Redis Checkpoint | Redis Lock |
| --- | --- | --- |
| 解决的问题 | 流程 **暂停后记住做到哪一步/可从存档续** | 防止 **多个 Worker 同时处理同一食材** |
| 生命周期 | 跟一次线程号(thread)一起存在直到流程跑完/被清理 | 只在“处理单个食材的那段关键代码”持有，用完后释放 |
| 类比 | 游戏存档 | 仓库门的锁 |
| 谁在用 | LangGraph 恢复流程 | 自动采购；人类审批 |
| 失败了会怎样 | 无法从暂停恢复（有 DB 重建兜底） | 抢不到锁就跳过该食材（fail-closed，绝不绕过） |

> 强记：**Checkpoint ≈ “记得下一步做什么”，Lock ≈ “别两个人抢同一件”。** 它们只是碰巧都依赖 Redis，但完完全全不是一回事，绝不能混为一谈。

---

## 4. 如果你担心：Redis 挂了怎么办

简单如实说：本 MVP里没有为 Redis 挂掉专门做自治保障，它是正常运行的前提之一。
- Lock 没了 → 并发保护失效（在带人工审批的 MVP 风险可接受，生产化要 Redis HA）。
- Checkpoint 没了 → 暂停恢复弱化（代码里有从 DB 重建字段的兜底跑路）。
我们把数据库(MySQL)当“真正的真账本”，Redis 是辅助性的“内存档 + 门上锁”。顺带说明：文档里我们不声称有 watchdog/Redlock/自动续期之类没实现的能力。
