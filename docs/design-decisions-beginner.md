# 为什么这样设计？· Design Decisions for Beginners

> 每次设计都按这个套路想明白后再讲：
> **当时遇到什么问题 → 最直觉的做法 → 为什么不够 → 最终方案 → 为什么选它 → 代价/边界 → 以后怎么升。**
> 看完这页，你会懂这套系统不是“为了炫技”，而是为了责任与稳定而权衡出来的。

---

## 决策 1：Agent1/2/3 用确定性 Python，而不是让 LLM 算库存/价格/数量

**问题**：系统需要库存够不够、价格贵了多少等能直接转账的数字。
**直觉做法**：把食材数据丢给一个聊天机器人，让它返回“看起来合理”的结论。
**不够**：LLM 是对“文字”做概率生成，加减乘除会飘（可能把差值算略错、把话扯远）。金额/库存错一点就是实打实记错账。
**最终方案**：库存/价格/供应商这三个分析由**确定性 Python** 完成，输入相同输出永远相同，一步都不会多不会少。
**为什么**：需要精确、可复现、可排障的地方交给不会胡来的代码；只有“把它讲成人话”这种没有绝对答案的事才该给小模型/大模型。
**代价/边界**：模型表达能力没用在这三个分析上；未来若要“聪明地理解行情”等再加。
**以后可升**：可把“多因子”（保质期、批次、在途）加进确定性逻辑，但仍是规则，不是让模型来算金额。

**类比**：算钱找计算器，别找会说会押韵的演说家。

## 决策 2：为什么要一个 `deterministic_policy`

**问题**：三个分析的各自结果要拼起来，才能“要不要买”一并答。
**直觉**：把结果贴给某个会用人工判断的业务员(AI)让它自由发挥。
**不够**：要不要买背后是你定的“制度”，不是随心情或随机；金额与风险闸口要有人可审。
**最终方案**：单独一个 `determinetic_policy` node，用写死的 if/规则算出三类结局`NO_PURCHASE/PURCHASE/REVIEW`，并产出 `quantity / total_amount / risk_flags`。
**为什么**：制度要白纸黑字、能审计、能测试；放它且只放它一处，方便日后改一条规则就改这一处。
**代价**：规则很直(3天乘日销量)；未来要动态调安全线会有点硬。
**以后可升**：可把很多分阶规则、配置项等引入，但主体仍保持“可读、确定”。

**类比**：公司的采购制度表，而不是给每个采购员一支自动判断的算命签。

## 决策 3：Agent5 只解释风险 / 建议，不能改数量/状态或绕过制度

**问题**：光有“REVIEW”标签不成，得有人看懂“为什么是高风险、有多大、怎么办”。
**直觉**：干脆派一个会用嘴的 Agent，让它顺带决定要不要买、够不够补。
**不够**：如果让 Agent 自己把 REVIEW 改成 PURCHASE、自己改掉采购量——货币与库存决策就落到可以被模型幻觉污染的“黑盒”上。
**最终**：Agent5 只是读前面算好的 facts，返回一段结构化**建议文本**(概况/等级/分析的说明/建议)，不写数据库、不更评价 quantity/status。
**为什么**：真正能验证、可扛责任的决策与数字仍由制度和 HITL/人工兜底，Agent5 只在“供人参考”层面出力。
**代价/边界**：Agent5 内容质量受本地 LLM 影响；有安全回退(网络失败也给一个保守的兜底话)。
**以后可升**：可加更丰富 prompt/知识，但始终不让它在关键落库路径上拥有改键位。

**类比**：风险分析师写“报告建议”，批准权与改订单权在领导(人工)手里。

## 决策 4：REVIEW → HITL(人工) 而不是自己定高风险单

**问题**：价格异常 / 库存贴线的单子，机器要不要直接照规矩执行？
**直觉**：按“价格>20% 就拒绝”简单化 — 但很可能市价确实涨了不补也不行，而简单“自主放行”也缺人承担责任。
**不够**：完全自动/完全拍死都失衡——自动漏人审、拍死又无视合理行情。
**最终**：这类 REVIEW 会挂起等待一个真人的「通过 / 拒绝」（HITL）；系统不自己落明主。
**为什么**：高风险含大量背景与责任，交给“看得懂的人拍板”最合适，程序只负责把风险讲清(Agent5)并提供恢复手段。
**代价/边界**：需要人工等待，天然有延迟；补单不能立即冲到底。
**以后可升**：可加消息提醒、超时兜底、给审批做 RBAC。

**类比**：超过系统预算的补仓不能自动花，要领导批。

## 决策 5：Redis Checkpoint 与 Redis Lock——两件完全不同的事

**问题**：流程想“暂停等人完继续”，又想“多 Worker 别打同一食材”。
**直觉**：都是 Redis，会不会一种就够了？
**不够**：单独用 Lock 不能记住“停在哪一节点”；单独用 Checkpoint 更不能拦另一个 Worker。
**最终**：
- **Checkpoint**负责存「中断到了哪个节点 + 该线程的状态」，供 APPROVE恢复续跑——像游戏存档。
- **Lock**负责「同一食材同一时间只放一个流程进入」，防重复采购——像仓库门锁。
是**Redis 提供能力的两用**，在项目里 key 和语义都分开。
**为什么**：一个管“流程时间旅行”(从停点续跑)，一个管“并发互斥”(别重复)。位置都在 Redis 纯因为要快速共享。
**代价/边界**：MVP 里 Lock 是固定 TTL、没有 watchdog/续期；生产要再考虑 Redis HA 与续期。
**以后可升**：为 Lock 补续期 / 集群高可用；Checkpoint 若丢可用 DB 字段重建兜底(已有部分)。

**类比**：一个硬盘分区存进度档，另一个专门给门锁；不是同个“存档”。

## 决策 6：`policy_decision.quantity` = 采购数量的唯一真相

**问题**：谁是“真要买 20”的正主？历史字段常混(当时 state.quantity 一直是 0)。
**直觉**：随手找个变量读。
**不够**：不同模块对一个数据“到底放哪”理解不一致，早期就出 bug——“看着建单成功、实际库存从没加”。
**最终**：把 Rule 产出的 `policy_decision.quantity` 定为唯一“该买多少”，Service 只认它，把它写入 `purchase_order_items.quantity`，再 `execute_inbound_stock` 用明细数量把 `inventory.current_stock` +N。
**为什么**：一份数据只在最权威处生成，读方也认同一份，避免契约错位。
**代价/边界**：从 decision 到 DB 至少要经过写 order_item，不能直接拿成一个字段当日用就完。
**以后**：可引入明显类型/映射表、schema 注释把契约说死。

## 决策 7：自动采购需要“Ingredient Lock + DB open check + 入库幂等”三层

**问题**：多 Worker 同时发现某食材要补，可能建两张单、加两次库存(check-then-act)。
**直觉**: 只在数据库里检查“有没有进行中订单”。
**不够**: 两个 worker 先后“查都为空”，再各自建单仍会撞(竞态仍存在)。
**最终**: 
1. Ingredient Redis Lock —— 把同一食材的“查单→下单→入库”串行；
2. DB `_has_open_order`——账本再兜底一次(锁失效时也不重复)；
3. `execute_inbound_stock` 幂等——已 COMPLETED 的图绝不二次 +库存。
**为什么**: 三层分工互不替代，覆盖“并发互斥 / 数据现状 / 重复执行”。
**代价/边界**: Lock 固定 TTL；跨机器正确性建立在同用同一锁 key 与 Redis 可用上。
**以后可升**: 锁续期、队列化、数据库唯一约束，进一步加固。

**类比**: 门口锁防止别人同时进；进门再核对底账 (open) ；搬货系统本身保证一发不二发。

## 再加：为什么会用 LangGraph 而不是普通 Python 串函数

问题：流程有并行、暂停等人、继续不重跑。直觉是“写几个 Python 函数排头按尾调一遍” — 但那没法原生表达 interrupt/resume 与“并行”还能恢复的编排；硬写会越写越绕。LangGraph 把 node/edge/state/并行/interrupt/resume收成一套显式可测的图，节省了大量自造轮子。代价是多学一个框架的少量心智；换来可断点恢复、直观 DAG。

**为什么三个分析真能并行**：它们只读，各写自己那份（无相互依赖），工作图里让 START 同时分发再 Fan-in 到制度——并不互相抢同一字段，所以并行安全。

**Graph State 不是 MySQL**：state=这一次流程的临时共享本；MySQL=长期账本。临时态可丢/可重建；真正历史与真账数据只能 MySQL（详见 mysql-explained）。

**为什么 State 里既有 policy_decision.status 又有 state.status、DB 又有 orders.status**:它们各司其职——policy_decision.status 是制度判定(NO/PURCHASE/REVIEW)，runtime 的顶层 status 更多是流程态过渡，而 MySQL orders.status 是订单在系统里的业务/审批状态。混装会把“决策-流程-台账”三层黑成一锅，让人分不清改动的是哪个。

### 结尾诚实的边界一句话

以上都是 MVP 决策，做了很多“为了不把账搞错”的取舍；明确说，目前仍是 3 天预测的简单口径（不是真正3~7天健康区间），Supplier Analysis 是快照（非多供应商智能选优），Redis 锁固定 TTL 没续期。要落地更生产的能力，先补这几点，而不是宣称已经实现。
