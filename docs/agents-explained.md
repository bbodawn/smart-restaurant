# Agent 到底是谁？· Agents Explained

> 很多人看到“多 Agent”，第一反应是“好几个 ChatGPT 在开会”。
> 我们这个项目**不是那样**。这里先说清：**Agent 是一个"负责某类工作的角色"，不等于它一定是大模型。**

---

## 0. 一句话把“Agent”说清

Agent（代理）在这里＝**帮系统完成某一件具体事的小分工的角色**。

- 它可能是“套着人皮的固定算法”（干减法、记表格、按制度判断）。
- 它也可能是“会说话的大模型”（把风险写成一段人话）。

**关键记忆：会用大模型 ≠ 一定要用大模型；把项目叫 Multi-Agent 也不代表用了很多 LLM。**

---

## 1. 项目里到底有哪几个“角色”

| 角色（业务的叫法） | 代码里对应的节点 | 它主要干什么 | 用大模型吗？ |
| --- | --- | --- | --- |
| 仓管员 / 库存分析 | `inventory_analysis` | 看现在还剩多少、够不够撑未来 3 天、覆盖天数 | ❌ 否（纯算术） |
| 价格检查员 / 价格分析 | `price_analysis` | 算当前报价比历史均价贵了几个百分点 | ❌ 否（纯算术） |
| 供应商登记员 / 供应商分析 | `supplier_analysis` | 只照抄“这家供应商是谁、报价多少”当快照 | ❌ 否（照抄） |
| 制度表 / 规则裁判 | `deterministic_policy` | 按写死的制度决定 不买/自动买/请人审，以及买多少 | ❌ 否（固定规则） |
| 风险顾问 / 解释 Agent | `agent5` (Agent5) | 把“为什么触发复审、风险、建议”写成自然语言段 | ✅ 是（LLM） |

> **注意**：上一个我把它当成“Agent”，但严格讲 `deterministic_policy` 更像一段制度判断，而不是 Agent；真正的“会说话的分析角色”是 Agent5。别在架构描述里硬塞 5 个真 LLM。

## 2. 各角色分头讲（人话）

### Agent1 / 库存分析（仓管员，不看大模型）
- 输入：当前库存、日销量、安全库存。
- 输出：还能撑几天、距离未来 3 天还够不够。
- 为什么不用 LLM：因为这在算“40 减/比 60”这种简单的表，让 Python 算绝不犯错。
- 参考：`inventory_analysis`。

### Agent2 / 价格分析（价格检查员，不看大模型）
- 用固定公式算报价与历史均价的偏差百分比。
- 如果历史均价==0 之类怪情形，它保护性地把结果当 0，不会让除零把流程打崩。
- 为什么不用 LLM：百分比是一个该精确的数，不该让模型“大概口算”。
- 参考：`price_analysis`。

### Agent3 / 供应商分析（登记员，不看大模型）
- 只把当前这单用的供应商是谁、报价多少原样放出来。
- **诚实边界**：它只做快照，程序里没有“货比三家、自动选出最划算供应商”的能力。
  - 不要在文档或面试里吹成“智能供应商优选”。
- 参考：`supplier_analysis`。

### 规则裁判 / Deterministic Policy（制度表，不看大模型）
- 把三份分析拼在一起，按制度判断三种结局：`NO_PURCHASE`（不用买）、`PURCHASE`（风险低可自动买）、`REVIEW`（有风险要请人）。
- 还顺便把真正要买多少（`quantity`）也算好。
- 它是**整个采购决策的数字出处**：数量、金额、风险项都从这里来。
- 参见：`docs/langgraph-explained.md`、`docs/why-deterministic-policy.md`。

### Agent5 / 风险顾问（这段会说话，是用大模型的）
- 只在 `REVIEW` 登场。看前面算好的东西，把风险整理成一句话概况+ 风险等级 + 一段解释 + 给采购人员的建议（都是给人看的自然语言）。
- **权限非常小**：只能“建议/解释”，不能改数量、不能改制度结论、不能自己拍板买、不能碰数据库、不能绕过人工审批。
- 为什么要它：制度表能算出“该进复审”，但讲不清“为什么有问题、风险多大、怎么处理”——那段人话只能让能说话的大模型来。
- 参考：`agent5_node`（`nodes.py`）。

## 3. 破除一个最大的误区：为什么不让 5 个都是 LLM？

给你一道题：

> 库存 20，未来 3 天需求 50，需要买多少？

答案就是 `50 - 20 = 30`。这是个**加减法**。

你想让一个会一本正经胡说八道的大模型去算这种数字吗？（它可能算 29.5，也可能冒出 “30，但我觉得还是别买”）。所以这种“确定性算术”**交给 Python**。

再看另一道题：

> 供应商报价比历史贵了 25%，这意味着什么？该怎么跟采购的人解释？

这种没有标准答案、需要组织语言的活，才适合大模型。

于是整条认知就一句话：

> **确定性的东西交给代码，非确定性的解释交给 LLM。**

对应回角色：Agent1/2/3 + 制度表干“确定性”，Agent5 干“解释”。

---

## 4. 面试一句话总结（想不起来时背）

本项目是“Multi-Agent”架构，但**真正非确定性、需要自然语言理解与生成的是 Agent5（用 LLM）**；前置库存/价格/供应商分析与采购制度判断均为确定性 Python（算术与固定规则），把容易出错的百分比/买入量算得又稳又准，把必须解释给人听的风险又交给模型。这体现的设计是：**确定性→代码，分析/解释→LLM，授权与真正落库→人 + Service。**

## 5. 别碰这些红线（本项目没实现，别写）

- 多供应商自动比价/智能选商
- 真正的 3~7 天健康库存区间
- 高级需求预测模型
- Agent5 自动决定采购量、直接写数据库、绕过人工审批
- Redis Watchdog / Redlock / 锁的自动续期
- “AI 自主完成全部采购”

遇到这些说法如果你看到文档这样写，就说明它脱离真实代码了。
