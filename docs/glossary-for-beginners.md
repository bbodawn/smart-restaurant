# 技术名词小词典 · Glossary for Beginners

> 边看边当查字典用。每个词的套路一样：
> 一句话(人话) → 生活类比 → 在我这个项目里 → 为什么需要。
> 遇见不认识的就来这页查，不打断主流程阅读。

---

## Agent（代理 / 智能体）

- **一句话**：负责项目里某类具体工作的“角色”。
- **类比**：团队分工：有人管账、有人干事、有人只负责说话。
- **在我的项目里**：库存分析/价格分析/供应商分析/法规裁判/Agent5 都是不同“角色”；只不过前几个是写死算法，Agent5 才用大模型。
- **为什么需要**：把复杂流程拆成一小块一小块、各司其职、各自可测。

## LLM（大语言模型）

- **一句话**：很会“读文章、组织语言”的人工智能模型（像会聊天的机器）。
- **类比**：一个背书很厉害、能给你把事讲人话的顾问。
- **我的项目里**：只有 Agent5 用它，负责把风险解释成报告；**不**让 LLM 算数量。
- **为什么**：它适合解释、不适合做不能错的精确算术。

## Node（节点）

- **一句话**：图上某个“要干一小件事的岗位”。
- **类比**：一条流水线上的某个工位。
- **项目里**：`inventory_analysis`、`deterministic_policy`、`purchase_approval` 都是 node。
- **为什么**：让“谁干活”可编号、可单独测、可挨个看单。

## Edge（边 / 连线）

- **一句话**：两个 node 之间“做完就去找谁”的箭头/信号。
- **类比**：报表上一张“流程走完转给下一手”。
- **项目里**：例如 `inventory_analysis` → `deterministic_policy` 就是一条 edge。
- **为什么**：把流程画出来、方便阅读和管理执行顺序。

## State（状态 / 工作组）

- **一句话**：这段流程里大家共用的“一张工作表”，谁都能往上补结果。
- **类比**：一张大家轮流填的共享 Excel；谁写谁改大家都看得到。
- **项目里**：`analysis_inventory`、`policy_decision`、`agent5_analysis` 都往 state 里写。
- **为什么**：让不同“角色”之间交换数据有唯一去处、互相能拿到别人的成果。

## LangGraph（工作流传控制器）

- **一句话**：编排“谁在多节点之间按顺序/并行干活，还能暂停续跑”的流程引擎。
- **类比**：一个能把任务图排好活，并且在中间“存个档再继续”的调度器。
- **项目里**：把并行三分析 + 制度 + Agent5 + 人工审批串起来并支持 REVIEW 恢复。
- **为什么**：因为要并发 + 可随时暂停等人 + 之后不重跑，光靠一个 Python 函数链做不到。

## Graph（图）

- **一句话**：节点 + 线连起来形成的执行蓝图。
- **类比**：地铁线路图（站点=node，车次方向=edge）。
- **项目里**：`workflow.py` 里那套 LangGraph 蓝图。
- **为什么**：把整个系统的“谁能先走、谁汇到谁”可视化地表达。

## Fan-out（分叉并行）

- **一句话**：从一个地方出发，一下子给多个不同 worker 分发去并行干。
- **类比**：老板把活同时发给三个小组，大家分开做。
- **项目里**：BEGIN 同时把请求分给库存/价格/供应商三个分析。
- **为什么**：三者互不依赖，并行省时间。

## Fan-in（汇合）

- **一句话**：多个并行 worker 干完后回到同一个地方收口。
- **类比**：三个小组做完了都回来找老板汇报。
- **项目里**：三个分析做完都汇给 `deterministic_policy` 一起去判断。
- **为什么**：需要把多走结果汇总到一个决策点。

## Conditional Edge（条件分支）

- **一句话**：根据当前状态选走哪一条边的“岔路”。
- **类比**：红绿灯——风险低往左，风险高往右。
- **项目里**：制度表根据 status 把它送向 NO_PURCHASE / PURCHASE / REVIEW。
- **为什么**：决策的结果就是路由的依据。

## Policy（制度 / 规则）

- **一句话**：一套“固定条件下的动作结论”。
- **类比**：采购部的明文制度表。
- **项目里**：`deterministic_policy` 判断要不要买、要不要请人审、买多少。
- **为什么**：采购不能指望机器“自由发挥”，要按明确规则。

## Deterministic（确定性）

- **一句话**：输入一样，输出就完全一样，不随机、不靠模型猜。
- **类比**：1+1 永远 = 2。
- **项目里**：库存/价格/数量都用确定性计算。
- **为什么**：金额/库存这类不能出错，必须可复现、可审计。

## HITL（人在回路 Human-in-the-loop）

- **一句话**：让一个人参与流程中的关键决策（这里=审批）。
- **类比**：大额转账要经理批准，不自动放行。
- **项目里**：REVIEW 让人类点通过/拒绝后再执行入库。
- **为什么**：机器承担不了担责与看不清的风险判断。

## interrupt（中断 / 暂停）

- **一句话**：让当前工作流走到一半“停在这里，等补一个外部值”。
- **类比**：厨房做到一半把流程暂停等领导拍板。
- **项目里**：`purchase_approval` 里等人给 approved 值。
- **为什么**：打开一个“需要人类输入”的孔，让流程真正停下来等人。

## Command（命令对象）

- **一句话**：告诉图谱“用这个输入给暂停点继续/跳去下个节点”的“控制命令”。
- **类比**：领导说“继续干”，机器拿这去唤醒存档。
- **项目里**：`Command(resume={"approved": True})`。
- **为什么**：把“外部给的答案”带回被 interrupt 的流程。

## Checkpoint(存档点)

- **一句话**：把工作流“我跑到哪儿了/哪个步骤”记录下来，便于恢复。
- **类比**：游戏存档。
- **项目里**：REVIEW 前存到 Redis，审批后从它继续而非重跑。
- **为什么**：人审停很久/服务重启后仍能从原样继续。

## Redis Lock（分布式锁）

- **一句话**：跨多进程/机器保证“同一时间只有一个人能碰某个资源”。
- **类比**：仓库门锁。
- **项目里**：按食材锁，防多个 Worker 同事同一食材。
- **为什么**：让“查→下单→入库”这段不被并发打穿。

## Distributed Lock（同 Redis Lock 的意义、突出“跨机器”）

- **一句话**：即使代码在多台机子上，也保证互斥地属于同一把锁。
- **类比**：不只拦同一层楼的你，还能拦另一个楼同一房间号的人。
- **项目里**：自动巡检多 Worker 就是这个场景。
- **为什么**：单台内存锁拦不住另一台机器上的并发。

## Idempotency（幂等）

- **一句话**：同一操作无论执行几次，业务结果都是一次的效果。
- **类比**：快递因网络点两次，不能真的发两箱。
- **项目里**：入库 `execute_inbound_stock` 对已完成订单不再 +库存。
- **为什么**：网络重试/重复触发也不能重复入库。

## Transaction（事务）

- **一句话**：把几件事打包成“要么全成功、要么全失败”的单位。
- **类比**：一笔走账：扣钱和加余额必须一起成功。
- **项目里**：加库存 + 标订单完成放在一个事务提交。
- **为什么**：防止出现“库存加了但订单没完成”这类半中间态。

## Service（服务层）

- **一句话**：真正做业务、读写数据库的普通后端层。
- **类比**：负责真正把钱转出去的出纳。
- **项目里**：`execute_inbound_stock()`、自动巡检等都在 services。
- **为什么**：把真正的落库/库存逻辑和流程编排分离，便于事务与复用。

## API（接口）

- **一句话**：让外部“调一下就触发某种操作”的 HTTP 入口。
- **类比**：餐厅点菜柜台。
- **项目里**：`POST /api/v1/purchase`、审批接口等。
- **为什么**：让网页/客户端能与后端打交道而不直接碰代码。

## MySQL（关系数据库）

- **一句话**：长期保存结构化业务数据的库（账单、库存都用它）。
- **类比**：真正的总账本。
- **项目里**：存订单、采购明细、库存、供应商。
- **为什么**：持久、稳定、有事务，是“真账”。

## Redis（内存键值缓存 / 辅助状态）

- **一句话**：一块高速临时存取，用作“存档”和“锁”。
- **类比**：便利贴墙 + 门锁柜。
- **项目里**：LangGraph Checkpoint、食材锁/订单锁。
- **为什么**：不重跑流程 / 并发互斥要极快可用的中间件。

## Async（异步）

- **一句话**：让你“去干别的、等结果回来再继续”，不占着一个线程死等。
- **类比**：点上菜先刷手机，菜好再回去吃。
- **项目里**：async 的 service/graph 调用（LangGraph 异步运行）。
- **为什么**：网络/IO 时不空转，能支持并发高效。

## Worker（工人 / 工作进程）

- **一句话**：一个独立执行任务的实例/进程。
- **类比**：店里一名可以同时开工的伙计。
- **项目里**：Auto Procurement 可以跑多个 Worker。
- **为什么**：想并行时就要多实例——但也带来“并发互斥”要处理(锁)。

---

> 收起本页时若还记住两个，请你记住：**Deterministic→给 Python、解释→给 LLM/Agent5、授权→给人、真正落单入库→Service+MySQL；Checkpoint ≠ Lock，State ≠ MySQL。**
